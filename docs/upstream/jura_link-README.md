# jura_link: ESPHome Jura dongle component

`jura_link` turns an ESP32 wired to a Jura machine's service port into a replacement for the Jura
WiFi/Bluetooth dongle. It runs the dongle handshake, polls product and maintenance counters, decodes the
alert broadcasts, and publishes everything to MQTT with Home Assistant / openHAB discovery. The MQTT topic
layout matches the **jura-mqtt** BLE→MQTT bridge, so the dongle can replace a Bluetooth setup without changing HA/openHAB entities.

It is **read-only by default**: nothing it sends on its own brews, changes settings or writes EEPROM. Brewing and the panel lock
are opt-in (`allow_brew`, `allow_lock`).

| File | Role |
|---|---|
| `protocol.h` | Portable UART engine: 4-bytes-per-character encoding, framing, request queue, timeouts. No ESPHome dependency. |
| `jura_cipher.h` | `&`-frame cipher and escaping for the encrypted `@` dongle protocol. |
| `jura_link.h/.cpp` | ESPHome adapter: handshake, polling, stats/alert parsing, MQTT publishing. |
| `jura_jprf.h` | Reader for the packed machine-profile database (JPRF). |
| `jura_profiles_blob.h` | The database itself, generated by `tools/pack_profiles.py` (75 machines with products, brew options, maintenance labels and alerts, ~113 KB). |
| `__init__.py` | YAML schema and code generation. |

Protocol notes live in `AT-PROTOCOL.md`.

---

## 1. Hardware

- ESP32-C3 (tested: `esp32-c3-devkitm-1`), UART **TX GPIO20 / RX GPIO21**, **9600 8N1**.
- Only one component may consume the UART's input, so don't also enable an ESPHome UART debugger on the same bus.

## 2. Quick start

```yaml
esphome:
  name: jura-dongle
  on_boot:
    priority: -100
    then:
      - delay: 8s
      - lambda: 'id(coffee_link).start_handshake();'

web_server:          # keep it: with no serial console it is the only log/control path
  port: 80

mqtt:
  broker: 192.168.1.10   # your MQTT broker
  discovery: false   # jura_link publishes its own discovery from the machine profile

external_components:
  - source: github://harryzz/jura-uart-esphome
    components: [jura_link]

uart:
  id: jura_uart
  tx_pin: GPIO20
  rx_pin: GPIO21
  baud_rate: 9600

jura_link:
  id: coffee_link
  uart_id: jura_uart
  update_interval: 60s
  auto_poll: true
  mqtt_discovery: true
  # machine_model: "S8 (EA)"   # optional override, see section 5
```

This yaml doesn't name the machine anywhere. The dongle identifies the machine from its own reply, loads the matching profile,
and creates the entities for it.

## 3. Configuration options

| Option | Default | Meaning |
|---|---|---|
| `update_interval` | `30s` | Poll period. |
| `auto_poll` | `false` | `true`: each update runs the full stats poll (section 4). `false`: only a clear-text `TY:` identification. |
| `response_timeout` | `3s` | Per-request reply timeout (100 ms – 30 s). |
| `mqtt_discovery` | `false` | Enable MQTT state and discovery publishing (section 6). |
| `machine_model` | `""` | Override the model name. Empty = auto (section 5). |
| `machine_id` | `""` | Override the topic/unique-id id. Empty = slug of the model. |
| `base_topic` | `jura` | Root of the state topics. |
| `discovery_prefix` | `homeassistant` | Root of the discovery topics. |
| `allow_brew` | `false` | Brew over MQTT (section 6). **A Brew press makes the machine pour.** |
| `allow_lock` | `false` | **Panel Lock** switch over MQTT (`@TS:01` / `@TS:00`). |
| `ignore_alert_bits` | `[12,13,36,37,148,149,150,151]` | Alert bits that are never published. These are the jura-mqtt defaults: heating up, coffee ready, and similar non-problems. |
| `listen_only` | `false` | Never transmit. Received frames are only logged. |
| `sniff` | `false` | Raw capture mode: logs every idle-gap burst losslessly and bypasses the engine. Needs no TX pin, and implies `listen_only`. |
| `sniff_tag` | `rx` | Label for sniff log lines, so two sniffers on different UARTs stay distinguishable. |
| `connected`, `machine_type`, `last_reply`, `last_broadcast`, `last_error`, `at_decoded` | – | Optional diagnostic binary/text sensors. |
| `requests`, `replies`, `timeouts`, `unsolicited_frames`, `framing_errors`, `rejected_requests` | – | Optional diagnostic counters. |

Lambda API on `id(coffee_link)`:

- `start_handshake()`
- `poll_stats()`
- `query_type()`
- `query_at("@TF:")`, which sends any `@` command. **Careful:** `@TM`/`@TP`-style commands change the machine.
- `handshake_done()`
- `product_count(code)`, `maint_count(i)`, `maint_percent(i)`

## 4. How it works

### Handshake

Data commands only get an answer after the dongle handshake:

```
TX @T0 → @t0      TX @T1 → @t1
machine @T2:01C000  → TX @t2:818000     (fixed reply, see limitations)
machine @T3:3C16EF536M V02.01 → TX @t3  → the machine is identified here
```

The handshake runs from the yaml `on_boot` (+8 s) and whenever `poll_stats()` finds `handshake_done()` false.

### Polling

Each `update_interval` with `auto_poll: true` does the following:

1. **Product counters:** 12 banks, `@TR:32,00` … `@TR:32,0B`. Each bank holds 4 big-endian 16-bit words, and the word at index
   `bank*4+i` is the product with that XML code. Index 0 is the grand total.
2. **Maintenance counters:** `@TG:43`, one 16-bit word each, in the XML's `MAINTENANCEPAGE` order.
3. **Maintenance percentages:** `@TG:C0`, one byte each.

### Alerts

The machine broadcasts `@TF:<hex>` about every 2 s. It is the alert bitfield: **bit i = byte i>>3, most significant bit first**.
The bit names come from the XML's `<ALERT Bit Name Type>`. Example from the live S8:

```
@TF:002400000000 → bits 10 ("no beans" = display "fill bean container") and 13 ("coffee ready", ignored)
@TF:000400000000 → only "coffee ready": no alert
```

Alerts with `Type="block"` stop the machine from brewing. They set `status` = `blocked`.

## 5. Machine identification and naming

The `@T3` reply (or the `TY:` reply) gives a string such as `EF536M V02.01`. The profile database is searched for the
**longest matching EF code**, so `EF532V2…` gets the EF532V2 profile, not EF532's.

The model name, and from it the topic id, is chosen in this order:

1. The `machine_model` yaml override, if set.
2. The model family stored in the database for that EF code. For example, EF536 → **"S8"** → id `s8` → `jura/s8/...`.
3. The EF code itself, for example `EF1106` → `jura/ef1106/...`.

The family comes from `JOE_MACHINES.TXT`. One EF code covers many articles, for example EF536 covers S8, S8 (EA), S8 (SA), S80 and S808.
The packer strips region, Hz and "JURA " from those names and keeps the most common family. On a tie it stores no name.
68 of the 75 machines have a family name. The serial link reports only the EF code, never the article number, so a regional variant such as
"S8 (EA)" can't be detected automatically. The BLE bridge can do it because it reads the article number from the Bluetooth advertisement.

**Override for one specific machine.** To keep the ids of the existing jura-mqtt bridge, and with them the HA entities and history, pin them:

```yaml
jura_link:
  machine_model: "S8 (EA)"   # → machine_id s8_ea → jura/s8_ea/...
```

**Remove the override when the dongle moves to another machine.** Otherwise the new machine is published under the old name.

## 6. MQTT

### State topics

All state topics are retained and published only when a value changes. The dongle also resends everything every 5 minutes and after every MQTT reconnect.

| Topic (`jura/<id>/…`) | Value |
|---|---|
| `availability` | `online` / `offline` (MQTT birth, will and shutdown messages) |
| `connection` | `ON` if an `@` frame arrived in the last 10 s, else `OFF` |
| `rssi` | ESP WiFi RSSI in dBm |
| `status` | `blocked` (a blocking alert is active) / `ready` (link alive) / `idle` |
| `active_alerts` | Names of the active, non-ignored alerts, comma-separated, or `none` |
| `alert/<slug>` | `ON` / `OFF`, one topic per named, non-ignored alert |
| `total_products` | Grand total |
| `product/<slug>` | Per product, **including inactive ones** such as `powderproduct` |
| `maintenance/<slug>_counter` | For example `decalc_counter`, `cappu_rinse_counter` |
| `maintenance/<slug>_percent` | For example `decalc_percent`, `filter_change_percent` |

Values follow the jura-mqtt rules:
- A counter reading `0xFFFF` ("never used") is published as **0**. On the S8 this applies to the double products `2_coffee`, `2_espressi` and `2_ristretti`, whose counts the machine folds into the single products.
- A percentage is `min(v, 100)`, so `0xFF` → 100.
- A value that hasn't been polled yet is not published.

### Discovery

Each entity gets one retained message at `homeassistant/<platform>/<id>/<component>/config`. The component ids and names match jura-mqtt:
`connection`, `rssi`, `status`, `active_alerts`, `alert_<slug>`, `total_products`, `count_<slug>` (active products only),
`maintenance_<slug>_percent|_counter` and `refresh`. The device block is `{"identifiers":[id], "name":"JURA <model>", "manufacturer":"JURA",
"model":<model>, "model_id":<EF code>, "sw_version":"EF536M V02.01"}`.

The dongle sends 4 discovery messages and 10 state messages per second, so the MQTT TX buffer is never overrun.

### Commands

- `jura/<id>/refresh/set` (any payload; HA sends `PRESS`) runs `poll_stats()` immediately.

### Progress (always on)

| Topic (`jura/<id>/…`) | Value |
|---|---|
| `progress/percent` | whole-product progress 0–100, from the second-to-last byte of a 16-byte `@TV:` frame (100 at `enjoy`) |
| `progress/state` | `idle`, or the J.O.E. progress state, e.g. `coffee_bean_amount` (grinding), `coffee_water_amount`, `hotwater_volume`, `enjoy` (done), `add_beans`, `cleaning_process`, … Unknown codes show as `state_XX`. |
| `progress/product` | product (or maintenance process: Cleaning, Decalc, …) being made, `none` when idle |

These come from the `@TV:<state><code>…` frames the machine pushes while working (layout: jura-connect `docs/PROTOCOL.md` §5.10).
Frames with state `FE`/`FF` (aroma preselection, P-mode and accessory menus) and unknown codes are ignored. The dongle returns to `idle`
20 s after the last frame. HA sensors: Progress, Progress State, Progress Product.
Log lines: `BREW started` (`@TB` after our `@TP:`), `progress: <product> state XX, N%`, `BREW finished: <product>` (`@TV:3E…`).

### Panel lock (`allow_lock: true`)

The **Panel Lock** switch (`jura/<id>/lock`, command `lock/set` `ON`/`OFF`, same as jura-mqtt) sends `@TS:01` (lock) or `@TS:00`
(unlock), and the machine answers `@ts`. The switch state is read back from the machine: the `LockedKeys` alert bit (bit 39 on the S8,
`@TF` byte 4 `00`→`01`). It is correct even if something else locked the panel. If a machine's XML has no LockedKeys alert,
the last commanded state is shown instead. The real J.O.E. app wraps its reads in `@TS:01`…`@TS:00`, as seen in our sniffs.

### Brewing (`allow_brew: true`)

The entities match jura-mqtt, so its HA/openHAB controls carry over:

| Entity | Topic (`jura/<id>/…`, command = topic + `/set`) |
|---|---|
| select **Product** | `select/product`. Options are the active products. Selecting one resets the options below to that product's defaults. |
| select **Coffee Strength / Grinder Ratio / Temperature** | `select/<attr>`, pick-list ITEM names (union over products) |
| number **Water / Milk / Milk Foam Amount, Bypass, Milk Break** | `number/<attr>`, bounds = union over products (the value is clamped per product) |
| button **Brew** | `brew/set`: `PRESS` brews the selection. A product name as payload selects it and brews in one message. |

Brew builds the `@TP:` recipe blob (`jura_jprf::recipe_blob`, format verified by brewing, see makefu/jura-connect `docs/PROTOCOL.md` §5.9):

- 16 bytes: byte 0 = product code, and each option goes at byte `F<n>−1` from its XML `Argument`.
- Byte 8 = `01`, and all other bytes are `00`.
- Water and bypass are sent in 5 ml ticks. Strength, temperature and milk values are sent as-is.
- Values are clamped to the product's min/max and snapped to its step. An unknown pick-list value falls back to the default.

S8 Espresso defaults give `@TP:02000809000002000100000000000000`.
If the handshake isn't complete, the blob is held and sent right after `@T3`.

**Verified on the S8, 2026-09-18:** Coffee `@TP:03000514000001000100000000000000` poured 100 ml and the counter went up by one.
The log shows `BREW <product> @TP:…`, then `@bcast @TB` (started), `@TV:3C…` progress, and `@TV:3E<code>` (finished).
On serial there is no bare `@tp` ack; the dongle logs `BREW started` on `@TB` instead. A refusal would be `@tp:00` → `BREW rejected by the machine`. Blocking alerts (no water, grounds full, …) make the machine refuse.
Units follow jura-mqtt, which labels milk amounts `mL`. On the machine they are actually **seconds** (see jura-connect).

### Availability

The id is only known after the handshake. So once the machine is identified, the component points the birth, will and shutdown messages
at `jura/<id>/availability` and **reconnects MQTT once**. Don't set `birth_message` or `will_message` in the yaml.

### Not implemented

jura-mqtt's `switch/keep_awake` (a BLE-session thing, not needed here) and `button/power_off` have no serial implementation yet.
Retained configs left by the bridge still appear in HA, and because they share the availability topic they look available but do nothing.

## 7. Machine profile database (JPRF)

The generator is `tools/pack_profiles.py`. It reads `--xml-dir <dir>/<EFcode>/*.xml` and, optionally, `--machines JOE_MACHINES.TXT`
(model family names), then writes `components/jura_link/jura_profiles_blob.h` (and a raw `.jprf` with `--bin`).

```
header:  'JPRF' | u16 version(=4) | u16 machine_count | u32 strpool_off
index:   machine_count × { u16 ef_str, u16 name_str, u32 rec_off }      name = model family, "" if unknown
record:  u8 n_products; product[]: u8 code, u16 name, u8 flags(bit0 active, bit1 double), u8 n_opts,
           opt[]: u8 attr, u8 arg(F<n>), u16 def, u16 min, u16 max, u16 step, u8 n_items, item[]: u8 value, u16 name
         u8 n_maint_ctr; u16 label[]      (@TG:43 order)
         u8 n_maint_pct; u16 label[]      (@TG:C0 order)
         u16 n_alerts;  { u16 bit (bit15 = Type="block"), u16 name }[]
strpool: NUL-terminated UTF-8, referenced by u16 offset. All values are little-endian.
```

The reader refuses any version other than 4. Options cover the 8 attributes jura-mqtt knows. Sub-byte arguments (`F14_1`, `F2_H`) are skipped.

To add or change machines:

1. Get the machine files: the J.O.E. app ships one XML per machine (folder named by EF code) and `JOE_MACHINES.TXT`.
   They are Jura's files and are **not** included in this repository.
2. Run `python3 tools/pack_profiles.py --xml-dir <dir> --machines <JOE_MACHINES.TXT>`.
3. Rebuild the firmware. With `external_components` pointing at a local copy, the new header is picked up directly.

What the packer handles:
- Self-closing `<PRODUCT …/>` elements, such as Powderproduct.
- Alert names come from `Name`, not `Type`.
- EF codes are matched to `JOE_MACHINES.TXT` with `V2`, `_C`, `UL`, `PP` and `COFFEEONLY` suffixes stripped.

## 8. Build, flash, verify

Build and flash like any ESPHome config (`esphome run <config>.yaml`). Use OTA once the first USB flash is done.

**"OTA successful" doesn't prove the new image is running.** If the new app crashes within about a minute, the ESP32 silently
rolls back to the previous app. After every flash, check that the uptime restarted and that the new log lines or entities
show up at `http://<device-ip>/events`.

## 9. Diagnostics

- **Logs:** `curl -sN http://<device-ip>/events` (SSE with `event: log` and `event: state`). Decoded frames appear as
  `@reply …` and `@bcast …`, and profile selection as `profile EF536M V02.01: … -> MQTT jura/s8 (N entities)`.
- **Web API:** entity URLs use the full, URL-encoded name. For example:
  `POST /text/Jura%20AT%20Command/set?value=@TF:`
- **MQTT:** `mosquitto_sub -h <broker> -v -t 'jura/<id>/#'`.
- **Diagnostics yaml:** `examples/jura-dongle-debug.yaml` has handshake, status and free-text `@` command buttons plus all the diagnostic sensors.

| Symptom | Check |
|---|---|
| No MQTT data at all | Did the profile get selected (log line `profile …`)? That needs a completed handshake (`@T3`). Is `mqtt_discovery: true` set? |
| `no profile for EF…` | The EF code isn't in the database. Add its XML and regenerate (section 7). |
| Entities under the wrong name | A leftover `machine_model` / `machine_id` override (section 5). |
| Values stay `unknown` | That bank hasn't been polled yet. Check the `update()` / `@reply @tr:` log lines. |
| Data commands time out | The handshake wasn't done. Press the handshake button or call `start_handshake()`. |

## 10. Known limitations

- The `@T2` reply is a fixed constant (`@t2:818000`), not computed from the challenge. The challenge has always been `01C000` on the S8;
  other machines may need the real function, which lives in the encrypted dongle firmware.
- `poll_stats()` queues the handshake and the data commands together. Commands sent before `@T3` arrives can time out,
  and the next poll recovers them.
- `handshake_done()` is never reset on timeouts, and a failed boot handshake isn't retried automatically.
- Brewing is the only control exposed (`allow_brew`). Panel lock (`allow_lock`) is also exposed. Preselections (extra shot, and so on) and power off aren't implemented. **Never send `WE:`** (EEPROM write).
